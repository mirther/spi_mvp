## 2. Проблема

### 2.1. Проблематика

Алгоритмическая составляющая обработки сейсмических данных распределена по разным кодам и программным средам. Требуется объединить её в единую управляемую систему, которая обеспечивает:

- единый каталог физических исходных и производных файлов, зарегистрированных в проектах;
- импорт внешних сейсмических файлов во внутренний формат Dataset платформы с сохранением амплитуд, заголовков и структуры трасс;
- загрузку, изменение и сохранение рабочих Dataset между Pipeline Nodes;
- настройку логического порядка трасс и, в дальнейшем, геометрии и других характеристик данных;
- построение вычислительных схем из логических узлов и зарегистрированных модулей;
- определение порядка модулей внутри узлов и зависимостей между узлами;
- единый способ задания параметров и запуска алгоритмов;
- использование вычислительных ресурсов HPC-кластера через Slurm;
- мониторинг параллельного и последовательного выполнения узлов, модулей и заданий Slurm;
- сохранение конфигураций запусков, событий, диагностических логов и результатов;
- регистрация, учёт и повторное использование результатов обработки и диагностических данных.

Цель проекта — предоставить пользователю специализированный браузерный инструмент для организации вычислительной работы с сейсмическими данными: от регистрации физических файлов и настройки логического Dataset до построения Pipeline, его выполнения на HPC-кластере и учёта полученных результатов.

### 2.2. Границы MVP

В MVP платформа является персональной: пользователь работает под собственной Unix-учётной записью HPC и управляет своими проектами. Совместная работа нескольких пользователей над одним проектом, общая модель владения данными и разграничение прав внутри проекта не предусматриваются.

Для первой версии принимается следующий рабочий охват:

- основной внешний файловый формат импорта и экспорта — SEG-Y;
- ранее зафиксированный базовый scope MVP — одна 2D сейсмограмма и один зарегистрированный SEG-Y Data Asset на импортируемый Dataset;
- постоянное содержимое Dataset хранится в собственном бинарном формате платформы на HPC, а не в SEG-Y;
- Dataset включает реальные амплитудные массивы, заголовки трасс, технические метаданные и структуру/индексацию данных;
- PostgreSQL хранит каталог Dataset, версии, метаданные, связи, конфигурации и состояния выполнения, но не сами амплитудные массивы;
- рабочее представление Dataset с амплитудами находится в RAM вычислительного узла во время SLURM Job;
- исходные и экспортированные внешние файлы регистрируются как Data Assets; внутренние бинарные объекты Dataset не являются Data Assets;
- в MVP определены четыре типа операций переноса данных: `import_dataset`, `load_dataset`, `save_dataset`, `export_dataset`; встроенные научные модули FILTER, SORT, FOURIER и подобные не входят в поставляемый набор MVP;
- встроенная визуализация содержимого результатов не входит в MVP. Интерфейс показывает сведения о файлах и Dataset, их версии и расположение;
- все файлы SPI размещаются под `/home/user/spi`: физические Data Assets — в `storage/data/`, бинарные Dataset — в `storage/datasets/`, файлы запусков — в `runs/projects/pipelines/`, файлы PostgreSQL — в `database/postgres/data/`.

Разделение и объединение Dataset настраиваются на связях между Pipeline Nodes, а не реализуются отдельными модулями. Поздние примеры с 3D SEG-Y и `inline_start`/`inline_end` требуют подтвердить, расширяется ли ранее согласованный 2D scope MVP до 3D (**WIP**).

## 3. Пользователи и основные понятия предметной области

### 3.1. Пользователь

Пользователь — человек с персональной Unix-учётной записью на целевом HPC-кластере. Он самостоятельно запускает свой экземпляр Web App и открывает его в браузере, в том числе через SSH Tunnel. Пользователь работает со своими проектами и файлами. Доступ к файлам на уровне HPC ограничивается правами соответствующей Unix-учётной записи.

Точный механизм аутентификации пользователя в браузерном приложении, защита локального порта и проверка соответствия браузерного пользователя Unix-учётной записи должны быть определены в технической архитектуре (**WIP**). Наличие SSH Tunnel само по себе не считается достаточным механизмом аутентификации веб-приложения.

### 3.2. Основные понятия

| Понятие | Определение и использование |
|---|---|
| **USER** | Пользователь персонального экземпляра платформы. В MVP соответствует владельцу персональных проектов и Unix-учётной записи HPC. |
| **PROJECT** | Персональная рабочая область, объединяющая Data Assets, Datasets, Pipeline и результаты работы. |
| **COMPUTE PROFILE** | Сохранённый пользователем набор ресурсов SLURM для одного job: CPU, RAM, walltime и другие разрешённые параметры. Профиль принадлежит пользователю и доступен во всех его Projects. |
| **DATA ASSET** | Запись в PostgreSQL о внешнем физическом файле, например исходном SEG-Y или экспортированном SEG-Y. Хранит проект, имя, формат, путь, размер, checksum и технические метаданные. Физические файлы размещаются в `/home/user/spi/storage/data/{project_id}/`; имя таблицы PostgreSQL — `data_assets` — не меняется. Содержимое файла в PostgreSQL не переносится. |
| **DATASET** | Полноценный логический набор сейсмических данных платформы. Включает амплитуды, заголовки трасс, технические метаданные, оси отсчётов и структуру/индексацию. Данные физически хранятся в собственном бинарном формате платформы на HPC; PostgreSQL хранит описание и связи. |
| **WORKING DATASET** | Рабочее представление Dataset в RAM конкретного SLURM Job. Содержит фактические амплитудные массивы и необходимые заголовки/метаданные назначенной части данных. Последовательные модули одного job работают с общим объектом. Изменения становятся постоянными после `OUT` (`save_dataset`). |
| **DATASET VERSION** | Неизменяемое сохранённое состояние Dataset. Содержит полный набор данных в бинарном хранилище, включая амплитуды; в PostgreSQL хранится запись версии и ссылка на физическое представление/манифест. |
| **DATASET VERSION SOURCE** | Связь версии Dataset с исходным Data Asset или другими источниками происхождения. Позволяет сохранить provenance импорта. |
| **DATASET STORAGE** | Внутреннее бинарное хранилище Dataset в `/home/user/spi/storage/datasets/{project_id}/{dataset_id}/versions/{version_id}/`. PostgreSQL хранит каталог, метаданные, версии и ссылки на физические данные; точная организация бинарных файлов, манифестов и частей ещё подлежит проектированию. |
| **DATASET READER / WRITER** | Общий механизм чтения сохранённого Dataset в Working Dataset и сохранения Working Dataset обратно во внутреннее хранилище. Модули не должны самостоятельно разбирать физическую организацию бинарного формата. |
| **SEGYIN** | Модуль чтения внешнего SEG-Y. Выполняет чтение файла, парсинг заголовков и формирование Working Dataset в RAM. В сценарии импорта результат затем сохраняется через `OUT`. |
| **IN** | Модуль загрузки сохранённого Dataset или назначенной partition из внутреннего хранилища в RAM (`load_dataset`). |
| **OUT** | Модуль сохранения полного текущего Working Dataset, включая амплитуды и заголовки, во внутреннее бинарное хранилище и регистрации новой Dataset Version (`save_dataset`). Не формирует SEG-Y и не создаёт Data Asset. |
| **SEGYOUT** | Модуль экспорта сохранённого Dataset во внешний SEG-Y-файл (`export_dataset`). Экспортированный файл может регистрироваться как Data Asset. |
| **MODULE / MODULE DEFINITION** | Зарегистрированный компонент определённой версии. Для MVP каталог содержит модули импорта, загрузки, сохранения и экспорта. Пользовательские научные модули относятся к будущему расширению. |
| **PIPELINE** | Сохранённое описание вычислительной схемы проекта, состоящее из логических Pipeline Nodes и направленных связей между ними. |
| **PIPELINE NODE** | Логический узел графа Pipeline, не являющийся вычислительным узлом HPC. Узел содержит последовательность модулей и настройки выполнения. Источник Dataset определяется входными связями и первым модулем; не каждый узел обязан начинаться с `IN`. |
| **PIPELINE NODE MODULE** | Включение конкретного определения модуля в Pipeline Node. Порядок выполнения определяется порядком добавления модулей пользователем и сохраняется системой. |
| **PIPELINE NODE CONNECTION** | Направленная связь между Pipeline Nodes. Кроме зависимости может содержать настройки `partition` (разделение входного Dataset) и `union` (логическое объединение набора partition-результатов для следующего узла). |
| **PARTITION DEFINITION** | Настройка разбиения Dataset, размещённая на связи Pipeline Nodes. Содержит таблицу диапазонов или групп значений заголовков. Каждая строка соответствует отдельной partition и отдельному SLURM Job целевого Node Run. |
| **UNION** | Настройка связи, по которой результаты нескольких partitions рассматриваются следующим Pipeline Node как один логический Dataset после завершения необходимых upstream jobs. Физическая организация объединённого бинарного представления ещё уточняется. |
| **PIPELINE RUN** | Конкретный запуск Pipeline. Сохраняет статус, времена, порядковый номер запуска и snapshot графа, конфигураций, версий модулей, связей и ресурсных настроек. |
| **NODE RUN** | Фактическое выполнение одного логического Pipeline Node в рамках Pipeline Run. Может быть связан с одним или несколькими SLURM Jobs. |
| **SLURM JOB** | Задание на HPC для одной partition на одном вычислительном узле. Выполняет последовательную цепочку модулей соответствующего Node Run для назначенной части Dataset. |
| **MODULE RUN** | Фактическое выполнение одного Pipeline Node Module внутри конкретного SLURM Job/partition. Хранит статус, snapshot параметров, временные отметки и сведения об ошибке. |
| **EXECUTION EVENT** | Структурированное событие Pipeline Run, Node Run, Module Run или SLURM Job. Хранится в PostgreSQL и служит основой мониторинга и формирования журналов. |
| **ARTIFACT** | Самостоятельный научный результат модуля (например, спектр, модель или таблица). Создание Artifact пользовательскими RAM-модулями относится к будущему расширению и не входит в набор операций MVP. |
| **EXECUTION MANAGER** | Компонент управления графом Pipeline, создания Node Runs и SLURM Jobs, мониторинга Slurm, записи событий и обновления статусов. |
| **OPERATION TYPES** | Четыре типа операций MVP (`import_dataset`, `load_dataset`, `save_dataset`, `export_dataset`) описывают направления переноса данных между внешней файловой системой HPC, внутренним хранилищем Dataset и RAM. Описание приведено в `operation_types.md`. |

## 5. Функциональные требования

Критерии приёмки должны проверяться тестами или демонстрацией на целевом кластере. Требования к конкретным научным алгоритмам, допустимым параметрам и точности результатов определяются в спецификациях и документации соответствующих модулей.

### 5.1. Запуск приложения и проекты

**checked**

| ID | Функциональное требование | Критерий приёмки |
|---|---|---|
| FR-01 | Система должна предоставлять персональный Web App, запускаемый в контексте Unix-учётной записи пользователя на целевом HPC. | Пользователь запускает Web App под своей Unix-учётной записью как отдельное веб-задание на HPC и открывает интерфейс в браузере через предусмотренный способ подключения. Web App выполняет разрешённые файловые операции от имени соответствующей учётной записи; вычислительные задания модулей отправляются отдельно через Slurm. |
| FR-02 | Система должна позволять создавать, просматривать и переименовывать проекты пользователя. | Пользователь может выполнить перечисленные операции; после перезапуска Web App проекты и их состояние сохраняются. |
| FR-03 | Система должна обеспечивать привязку основных объектов работы к проекту. | Data Assets, Datasets, Pipelines и результаты обработки можно найти в контексте соответствующего проекта. В MVP объекты не становятся общими для нескольких пользователей. |

### 5.2. Регистрация физических файлов и работа с Dataset

**checked**

| ID | Функциональное требование | Критерий приёмки |
|---|---|---|
| FR-04 | Система должна позволять зарегистрировать внешний файл, который пользователь ранее разместил на файловой системе HPC. | Пользователь указывает путь или выбирает файл через доступный файловый браузер. Backend проверяет допустимость пути, существование и доступность файла, после подтверждения создаёт запись Data Asset. Исходный файл не копируется повторно. |
| FR-06 | При регистрации Data Asset система должна сохранять основные сведения о внешнем файле. | В записи доступны как минимум проект, имя, формат, путь/URI, размер и дата регистрации; при принятой политике вычисляется checksum. Технические метаданные SEG-Y могут сохраняться в PostgreSQL отдельно от содержимого файла. |
| FR-07 | Система должна проверять регистрируемый Data Asset и сообщать пользователю о проблемах. | Для неподдерживаемого формата, отсутствующего или недоступного файла, недопустимого пути либо ошибки чтения пользователь получает диагностическое сообщение. Проверка существования и доступности выполняется при регистрации Data Asset. |
| FR-08 | Система должна предоставлять просмотр технических метаданных SEG-Y и Dataset. | Пользователь может просмотреть доступные параметры исходного SEG-Y и сохранённого Dataset: число трасс, число отсчётов, интервал дискретизации, формат сэмплов, ревизию SEG-Y и поддерживаемые сведения заголовков. |
| FR-09 | Система должна поддерживать импорт зарегистрированного SEG-Y во внутренний Dataset платформы. | `SEGYIN` читает внешний SEG-Y на HPC, выполняет парсинг заголовков и чтение амплитуд, формирует Working Dataset в RAM. Затем `OUT` сохраняет полное содержимое Working Dataset во внутреннем бинарном хранилище HPC и регистрирует Dataset с первой Dataset Version в PostgreSQL. В MVP импортируется один зарегистрированный SEG-Y Data Asset на Dataset. |
| FR-10 | Система должна хранить постоянный Dataset в собственном бинарном формате платформы. | Внутреннее представление содержит амплитудные массивы, заголовки трасс, технические метаданные, оси отсчётов и необходимую структуру/индексацию. Амплитуды не записываются в таблицы PostgreSQL; БД хранит метаданные, версии и ссылки на физическое представление. |
| FR-11 | Система должна предоставлять общий механизм загрузки и чтения Dataset. | `IN` и Dataset Reader загружают сохранённый Dataset или назначенную partition из внутреннего бинарного хранилища в Working Dataset. Модулям не требуется самостоятельно указывать физические пути или разбирать формат хранения. |
| FR-12 | Система должна поддерживать Working Dataset с амплитудными массивами в RAM и сохранение его полного состояния через OUT. | Рабочее представление содержит амплитуды и необходимые заголовки/метаданные в памяти вычислительного узла. Последовательные модули одного SLURM Job используют общее состояние. `OUT` сохраняет полное текущее содержимое, а не только метаданные. Размер данных и рабочие массивы должны укладываться в фактически выделенную SLURM память job. |

### 5.4. Запуск и управление выполнением Pipeline

| ID | Функциональное требование | Критерий приёмки |
|---|---|---|
| FR-22 | При запуске Pipeline система должна создавать отдельный Pipeline Run и фиксировать снимок запуска. | Создаётся запись Pipeline Run со статусом, временем и снимком использованной структуры Pipeline, связей, версий модулей, конфигураций, Partition Definitions и ресурсных настроек. Последующее редактирование Pipeline не изменяет снимок уже созданного запуска. |
| FR-23 | Система должна управлять порядком запуска Pipeline Nodes на основании графа зависимостей и настроек связей. | Узел запускается после успешного завершения необходимых upstream узлов. Если входящая связь содержит `union`, целевой узел получает логический объединённый Dataset только после успешного завершения всех необходимых upstream partition jobs. Независимые готовые ветви могут выполняться параллельно при наличии ресурсов. |
| FR-24 | Внутри каждого SLURM Job система должна запускать модули Pipeline Node последовательно в сохранённом порядке. | Следующий модуль partition не стартует до успешного завершения предыдущего модуля в том же job. При ошибке текущая последовательность этой partition прекращается. Остальные partition jobs продолжают выполняться; новые jobs продолжают отправляться по мере освобождения слотов. Node Run получает `failed`, если хотя бы одна partition завершилась неуспешно. Независимые ветви Pipeline при ошибке одной из них — отдельный открытый вопрос. |
| FR-25 | Система должна создавать отдельные записи фактического выполнения Node Run и Module Runs. | Для выполняемого Pipeline Node создаётся Node Run. Для каждого фактически выполняемого модуля в каждой partition создаётся Module Run, связанный с соответствующим SLURM Job и размещением модуля в Pipeline. В Module Run сохраняются параметры на момент запуска, временные отметки, состояние и сведения об ошибке. |
| FR-26 | Система должна отправлять в Slurm отдельное вычислительное задание для каждой partition Node Run. | Execution Manager формирует job script с ресурсами выбранного Compute Profile, отправляет один job на одну partition и сохраняет Job ID. Job выполняет всю последовательность модулей узла для назначенной части Dataset. Число одновременно активных jobs не превышает заданного для Pipeline Node лимита. Вычислительные задания отделены от Web App; модули не управляют графом Pipeline и самостоятельно не отправляют jobs. |
| FR-27 | Система должна поддерживать связь одного Node Run с одним или несколькими SLURM Jobs. | При наличии разбиения для каждой строки Partition Definition создаётся отдельный SLURM Job на одном вычислительном узле. Каждый job выполняет цепочку модулей соответствующего Node Run для своей partition. Module Runs относятся к соответствующим SLURM Jobs. Гарантия размещения разных jobs на разных физических узлах проверяется с учётом политики целевого Slurm-кластера и остаётся открытым техническим вопросом. |
| FR-28 | Система должна отслеживать состояние SLURM Jobs и отдельно фиксировать результат выполнения модулей. | Для каждого job сохраняются доступные состояния Slurm, partition, вычислительный узел, время отправки/старта/завершения, exit code, пути к stdout/stderr и сведения о ресурсах. Результат каждого Module Run фиксируется по событиям worker/application. Статус Slurm `COMPLETED` сам по себе не считается достаточным подтверждением успешного выполнения модулей: должна быть зафиксирована успешная обработка соответствующих модулей. Состояние завершённого job уточняется через доступные средства учёта Slurm. |

## 6. Принятые архитектурные положения и вопросы WIP

### 6.1. Положения, используемые при проектировании MVP

1. **Session отсутствует.** Project объединяет Data Assets, Datasets и Pipelines; Pipeline Run фиксирует каждый отдельный запуск.
2. **Pipeline и Pipeline Run — разные сущности.** Pipeline является редактируемым описанием графа; Pipeline Run — отдельный факт выполнения со snapshot конфигурации.
3. **Pipeline Node — логический узел графа, а не вычислительный узел HPC.** SLURM Jobs создаются для выполнения partition данных.
4. **Порядок модулей задаётся порядком добавления.** Модули внутри одного SLURM Job выполняются последовательно; зависимости между Pipeline Nodes задаются связями графа.
5. **Data Asset и Dataset различаются.** Data Asset описывает внешний физический файл, например исходный SEG-Y или экспортированный SEG-Y. Dataset — полноценный набор сейсмических данных во внутреннем бинарном формате платформы.
6. **Dataset содержит амплитуды.** Амплитудные массивы, заголовки и структура данных сохраняются в бинарном Dataset Storage на HPC. PostgreSQL хранит каталог, метаданные, версии, связи и ссылки на физические данные, но не сами амплитуды.
7. **Working Dataset находится в RAM.** `SEGYIN` формирует рабочее представление при импорте; `IN` загружает сохранённый Dataset/partition. Последовательные модули одного job работают с общим состоянием.
8. **OUT сохраняет полное состояние.** `OUT` записывает Working Dataset, включая амплитуды, в Dataset Storage и создаёт новую Dataset Version. OUT не экспортирует SEG-Y и не создаёт Data Asset.
9. **SEGYOUT отвечает за внешний экспорт.** Он читает сохранённый Dataset и формирует SEG-Y; полученный файл может быть зарегистрирован как Data Asset.
10. **Operation Types описывают направления переноса данных.** В MVP используются `import_dataset` (HPC → DB), `load_dataset` (DB → RAM), `save_dataset` (RAM → DB), `export_dataset` (DB → HPC). Подробности — в `operation_types.md`.
11. **Partition и Union — настройки связей.** Разделение и логическое объединение не являются отдельными модулями; конфигурация хранится на `PIPELINE_NODE_CONNECTION`.
12. **Одна partition — один SLURM Job.** Один Node Run может включать несколько jobs; каждый job выполняет последовательность модулей своей partition. Module Runs фиксируют отдельные этапы внутри job.
13. **Compute Profiles принадлежат пользователю.** Профили содержат ресурсы одного job (CPU, RAM, walltime и разрешённые параметры SLURM) и доступны во всех Projects пользователя. Лимит параллельных jobs задаётся отдельно на уровне Pipeline Node.
14. **Ошибка одной partition не останавливает остальные.** Остальные запущенные jobs продолжают работу, новые jobs отправляются по мере освобождения слотов. Node Run получает failed, если одна или несколько partitions неуспешны; зависимый downstream node не запускается без успешного результата требуемых входов.
15. **EXECUTION_EVENTS и статусы — источник истины.** Статусы хранятся в PostgreSQL. `runtime.log` доступен во время выполнения; после завершения каждого SLURM Job формируется постоянный `runinfo.log` для его partition.
16. **Итоговый журнал создаётся на уровне partition job.** Каталог имеет шаблон `{pipelinenodename}_{executionnumber}_{partitionnumber}`. `stdout`/`stderr` сохраняются отдельно для системной диагностики; отдельные module logs не создаются.
17. **Перезапуск не является продолжением.** Каждый retry создаёт новый Pipeline Run с начала; предыдущие история и результаты не перезаписываются и автоматически не переиспользуются.
18. **Web App восстанавливает выполнение из PostgreSQL и Slurm.** После перезапуска Execution Manager сверяет активные Job ID с состоянием Slurm; наличие лог-файла не определяет статус.
19. **Пользовательские научные модули отложены.** В MVP реализуются операции импорта, загрузки, сохранения и экспорта. Расширение RAM → RAM с возможным прямым выводом RAM → HPC и пользовательские алгоритмы относятся к следующему этапу.
20. **Каталоги SPI фиксированы.** Все файлы размещаются под `/home/user/spi`: Data Assets — `storage/data/`, бинарные Dataset — `storage/datasets/`, запуски — `runs/projects/pipelines/`, PostgreSQL PGDATA — `database/postgres/data/`. Каталог `storage/data/` не меняет имя таблицы PostgreSQL `data_assets`.

### 6.2. Вопросы, требующие уточнения

- **Физическая организация внутреннего бинарного Dataset.** Собственный бинарный формат принят. Необходимо выбрать: один файл или набор взаимосвязанных файлов, формат манифеста, индексов, блоков амплитуд и хранения заголовков.
- **Partition и Union в бинарном хранилище.** Логика partition/union на связях согласована. Требуется определить физическое представление набора partition-частей одной Dataset Version и правила публикации полного логического Dataset после завершения всех jobs.
- **Проверка Partition Definition.** Нужно определить правила диапазонов, пересечений, пропусков и полноты покрытия значений заголовков, а также поведение при отсутствии или некорректности нужного header.
- **2D/3D scope.** Ранее MVP был ограничен одной 2D сейсмограммой, тогда как поздние примеры используют 3D SEG-Y и inline ranges. Требуется подтвердить, расширяется ли MVP до 3D или эти примеры иллюстративны.
- **Trace Mapping и индексация.** Собственный бинарный формат должен позволять адресовать логические трассы и их физическое расположение без самостоятельного разбора storage layout модулями. Конкретная структура индексов ещё не выбрана.
- **Гарантия размещения jobs на разных физических узлах.** Логическая модель предполагает один partition job на одном вычислительном узле. Нужно проверить политику Slurm и определить необходимость `--exclusive` или другого ограничения размещения.
- **Политика ошибок независимых Pipeline Nodes.** Поведение partitions внутри одного Node Run согласовано: остальные jobs продолжаются. Действия для независимых ветвей при ошибке одной ветви ещё не определены.
- **Ограничения Compute Profiles.** Пользовательские профили и их область действия согласованы. Необходимо проверить у администраторов допустимые значения CPU/RAM/walltime, доступные Slurm partitions/queues и дополнительные ограничения.
- **Аутентификация Web App.** Нужно определить механизм аутентификации браузерного пользователя, защиту порта и подтверждение соответствия Unix-учётной записи. SSH Tunnel сам по себе не считается полноценной аутентификацией приложения.
- **Порты Pipeline.** В MVP связь может задавать зависимость и параметры передачи Dataset между узлами. Необходимость явных адресуемых input/output ports требует отдельного решения.
- **Межпроектное использование данных.** Базовый сценарий MVP — повторное использование Dataset и Data Assets внутри одного Project. Правила использования между Projects пока не определены.
- **Пользовательские модули и Artifact.** В MVP пользовательское создание RAM → RAM модулей и их Artifact outputs не реализуется. Требования к API модулей, изоляции, прямой записи Artifact и гайдлайнам разработки определяются на следующем этапе.
